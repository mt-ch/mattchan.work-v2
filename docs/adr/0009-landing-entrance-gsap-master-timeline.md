# Landing Entrance: one GSAP master timeline over the real stream nodes

The Landing Entrance is one GSAP master timeline, owned by a client component that wraps the page and finds its elements through `data-entrance` attributes. It animates the real stream and carousel nodes rather than a separate overlay, so there is no loader to hand off from and no second copy of the tiles. This extends ADR 0008: GSAP already runs only in client components, and the stream and carousel are created paused and started by the timeline's final step, which also marks the Entrance done so tile videos begin to load.

A tiny inline script in the document head runs on hard loads of `/` only and marks `<html>` as Entrance-pending (or with a reduced-motion variant). CSS gated on that mark hides the page and makes it inert until the timeline completes, so the finished layout never flashes. Client-side navigation does not re-run the script, so it shows no Entrance, and no sessionStorage is needed to remember that. A `<noscript>` style cancels the hiding so the page renders without JavaScript. The reduced-motion variant is a 0.4s page fade with no counter and no gate.

The Entrance's tunable values live in one typed config module. In development, `?entrance` mounts GSDevTools on the master timeline; the import sits behind a production check so it is not in production bundles.

On desktop the Entrance opens with a load gate, then a stack. The five stack images (the first copy of tiles 0–4) are preloaded at high fetch priority, and the gate waits for all of them to load and decode with no time ceiling. A failed image counts towards the gate but is dropped from the stack. The master timeline is built when the gate opens, because only then is the set of cards known. Until then the counter blurs in and climbs towards 40 through a smoothed side tween that only moves forward. The cards are moved with transforms measured at runtime from each tile's natural slot to a stack centred in the viewport, so a resize only has to clear the measurements and invalidate the timeline.

After the stack the timeline deals. The stacked cards travel back to their natural slots (the transforms return to zero) with a stagger, tile 0 first, counter-scaling their corner radius so corners do not swell. Every other tile node, including any card dropped from the stack, is left at the pre-hydration opacity and fades in with a rise over the last half of the deal. The sidebar then fades in as one block, starting before the deal ends, and the timeline's last step hands off. Inline opacity set by these tweens takes over from the page-wide fade variable, which only the plain fade path uses. A resize once the deal has begun, or crossing the desktop breakpoint in any phase, snaps the timeline to its end so the stream's own resize handling takes over and no card lands in a stale position.
